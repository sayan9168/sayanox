# String-value copy in the multi-ISA emitter — 2026-10-31

## Reviewed increment

`tools/native32.sa` accepts `hold b = a` and `b = a` when `a` is a declared
string variable, copying the 8-byte `(pointer, length)` pair of `a` into `b`.

- Value semantics, not aliasing: after `hold c = b`, reassigning `b` leaves `c`
  at its old bytes.
- Empty strings copy as length 0.
- Nothing is allocated: a copy cannot consume the 60 KiB concat heap, unlike
  `concat`.
- Implemented as three arch-independent load/store pairs through the existing
  `emit_load_global` / `emit_store_global` helpers with the `+4` field offset,
  so no new per-ISA instruction encoding was introduced.
- Refusals keep the boundary fail-closed: numeric source into a string
  destination and the reverse both report "a variable cannot change between
  numeric and string values" (previously a bare string name on the right of a
  numeric assignment was read as a number), an undeclared source is
  "unknown name", and arbitrary string expressions are still not sources.

## Found, not fixed (R14)

A program that *uses* `concat` initialises its literal temp slot in the data
segment with `literal_base + offset`, where `literal_base` is `134516736` on
i386 and `4198400` on AArch64/RV64IM. Each image is correct for its own target,
but the data segments differ, so the "three-way data-segment agreement"
assertion only covers programs without `concat`. This predates the copy work
(verified against the pristine emitter) and is registered as R14 with a fix
sketch: initialise those temp slots at runtime, or store an arch-neutral offset.

The first attempt on the same tree exited 1:

```
[OK] native tool: sxbuild
[FAIL] selfhost/seed_tests/sxbuild_gate/inv.out: pattern assertion: non-anchor .c/.h files: *0
sxbuild: target failed: test-sxbuild
EXIT=1
```

Cause: `selfhost/mini_out.c` (19061 B) was sitting in the working tree, left
behind by an ad-hoc compiler invocation earlier in the session. It is the
compiler's default output path, it is listed in `.gitignore` (line 28), and
`git status` therefore never showed it. `sxbuild`'s inventory walks the
filesystem, and `is_generated_c_artifact` only knows the checked-in generator
names plus the "has a `.sa` peer" rule, so this gitignored default output was
counted as a stray C source. `rm selfhost/mini_out.c` followed by
`./sx target test-sxbuild` gave exit 0 immediately, which isolated the cause;
the full chain was then re-run from scratch. The gate was not weakened: neither
the assertion nor the whitelist was edited. A clean checkout never contains the
file, so CI is unaffected, but the friction is registered as **R15** with the
one-line fix sketch (whitelist the gitignored default outputs and add a
fixture that proves both directions: generated output not counted, real stray
`.c` still counted).

## Second full-CI attempt: a stale pin chain, caught by `sxddc`

After the doc edits above, the next `./sx ci` exited 1 at
`test-native-bootstrap`:

```
[OK] native tool: sxddc
sxddc: failed run produced misleading receipt
sxbuild: target failed: conditional DDC harness refusal controls (not independent proof)
EXIT=1
```

The child log (`.../failed-run/input-entry-pins.log`) showed the real cause:

```
docs/full-language-v1.sha256: FAILED
sha256sum: WARNING: 1 computed checksum did NOT match
```

I had repinned `docs/full-language-v1.sha256` after editing
`docs/REMAINING_WORK.md` but not the entry for that manifest inside
`bootstrap/sx.sha256`, so the manifest was self-consistent while the entry
manifest that pins it was stale. Checking each manifest with
`sha256sum -c` in isolation does **not** catch this: the broken link is a
manifest pinning another manifest's bytes. `bootstrap/sx.sha256` now carries the
new digest, all three manifests verify together, and
`./tools/sxddc self-test` exits 0.

This is a real gate doing its job, not a flake; nothing was weakened. It is also
the reason the pin convergence step below ends with a single pass over *all*
manifests rather than one.
